# LearnFlow Embeddings

## Purpose

Define how LearnFlow converts eligible resource text and retrieval queries into vectors for semantic search.

An embedding model is separate from the AI chat/generation model. The embedding model helps find relevant source material; the AI provider uses selected material to generate an explanation, answer, or practice content.

## Initial Direction

LearnFlow starts with a local embedding provider configured for the local-first workflow. The specific embedding model name is configuration, not a hardcoded domain decision.

```text
Resource chunks ──► Embedding provider ──► ChromaDB index
Learner query ────► Embedding provider ──► Similarity search
```

The application depends on an `EmbeddingProvider` interface. It must not assume a specific provider SDK, vector dimension, or model name outside the configured adapter.

## Embedding Provider Responsibilities

The provider must:

- Convert one or more approved text inputs into numeric vector representations.
- Identify the configured model/version and vector dimension.
- Return vectors in the same order as requested inputs.
- Report unavailable-model and generation failures clearly.
- Support both document-chunk and query embedding use cases where required by the model/provider.

The provider must not:

- Store learner progress or resource ownership.
- Decide which sources are retrieved.
- Generate learner-facing mentor answers.
- Access arbitrary files outside the ingestion workflow.

## Model Selection Criteria

Choose the initial embedding model based on:

- Suitability for English technical/educational text, including GATE CSE terminology.
- Retrieval quality on representative learner notes and PYQs.
- Ability to run acceptably on the target local machine.
- Compatibility with the selected local provider/runtime.
- Stable model identification/versioning.
- License and redistribution suitability for the project.

Do not select a model only because it is popular. Validate it using representative GATE CSE retrieval queries before treating it as the default.

## Embedding Metadata

Every indexed resource representation must be traceable to:

```text
embedding provider
embedding model name/version
vector dimension
chunking-policy version
resource/content fingerprint
ingestion timestamp
```

This metadata makes it possible to diagnose poor retrieval and decide whether a resource needs re-indexing.

## Compatibility Rules

- Query embeddings and document embeddings searched in the same collection/index must be generated by compatible model configuration.
- Do not mix vectors from incompatible models or dimensions in one logical retrieval collection without an explicit migration strategy.
- A change in embedding model, dimension, normalization behavior, or chunking policy can require re-embedding.
- The original resource file and PostgreSQL metadata remain the authoritative source for rebuilding vectors.

## Re-Embedding Workflow

When the configured embedding model or incompatible chunking policy changes:

```text
Approve model/configuration change
       ↓
Record new embedding version
       ↓
Queue eligible resources for re-ingestion
       ↓
Create new vectors/index entries
       ↓
Validate retrieval quality
       ↓
Switch retrieval to the new compatible index
       ↓
Retire old derived vectors after verification
```

Do not delete original resources, learner progress, plans, assessments, or resource metadata as part of re-embedding.

## Privacy and Scope Rules

- Embed only text extracted from learner-authorized resources.
- Do not embed passwords, secrets, environment configuration, arbitrary machine files, or unrelated private data.
- Treat embeddings as potentially sensitive derived data; apply the same learner ownership/access filters used for resources.
- Keep embeddings local by default in the MVP.
- If a future cloud embedding provider is selected, clearly disclose that eligible chunk text will be sent to that provider.

## Failure Behavior

| Situation | Required behavior |
| --- | --- |
| Embedding model unavailable | Mark ingestion/retrieval dependency unavailable; do not report resource as searchable. |
| A chunk cannot be embedded | Record safe failure details; do not silently claim complete indexing. |
| Incompatible vectors detected | Prevent mixed retrieval and require a controlled re-index. |
| Model configuration changes | Re-index affected resources before using new query embeddings against them. |

## Quality Evaluation

Evaluate the selected embedding configuration using representative GATE CSE material and queries:

- Does “Explain deadlock” retrieve deadlock notes rather than unrelated OS text?
- Does topic filtering improve results when the learner selects a topic?
- Do PYQ-related queries retrieve PYQ content when available?
- Are semantically similar but wrong-topic chunks a frequent problem?
- Does retrieval remain useful with short notes and formula sheets?

Record evaluation findings before changing the default embedding configuration.

## Not Defined Here

- The exact model name or provider API.
- Exact vector dimension.
- Exact chunk-size/overlap configuration.
- ChromaDB collection naming and deployment implementation.

These are implementation/configuration choices guided by the compatibility and evaluation rules above.
